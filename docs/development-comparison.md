## 문서상의 설명과 실제 코드 구분

농구 README의 사고 과정은 설계 → 최소 기능 → 저장 → 모듈화 → 예외 처리를 설명한다. 실제 커밋 목록에서는 메인 화면 다음에 모듈화가 나타난다. 따라서 설명용 순서를 실제 개발 순서와 완전히 같다고 단정하지 않는다.

농구 README의 최소 예제는 정답 번호를 1부터 쓰지만 현재 quiz.py의 check_answer는 저장값에 1을 더해 비교한다. E1-2는 정답 번호를 1~4로 저장하므로 그대로 복사하면 안 된다. 또한 현재 play.py는 한 문제를 무작위로 고르는 방식이며, python-quiz는 목록을 섞어 한 판에 전체 문제를 푼다.

## 우리 방식에서 유지할 점과 바꿀 점

- 메뉴·입력·클래스·반복문의 효과를 실제 실행으로 확인하는 방법은 유지한다.
- 이미 익힌 문법은 한 줄씩 추가하기보다 한 기능으로 묶는다. 예: 입력 → 검증 → 정답 판정 → 결과 확인.
- 코드를 전달할 때 추가·수정 위치, 교체할 범위, 들여쓰기와 기대 결과를 함께 제시한다. 새 if를 중복으로 붙이는 혼동을 줄인다.
- Quiz.check를 이미 만들었으므로 입력 번호를 검증하고 숫자로 변환한 뒤 check에 전달하는 방향으로 통일한다. 현재의 문자열 직접 비교는 중간 학습 단계다.
- 한 기능 확인 후 임시 출력문을 정리하고 기능 단위로 기록·커밋한다.

## 앞으로의 구현 순서

1. 답 입력·번호 검증·정답 판정: 정답, 오답, 문자, 빈 입력, 범위 밖 번호를 확인.
2. 한 판 결과: 정답 개수를 누적하고 마지막에 정답 수와 점수 표시.
3. 목록·문제 추가: 목록 조회와 새 문제 입력을 구현하고 추가 문제 출제를 확인.
4. 최고 점수: 이번 판 결과와 이전 최고 기록을 비교.
5. QuizGame 구조 정리: 검증한 기능을 메서드로 묶고 메뉴·문제 목록·점수를 관리.
6. JSON 저장·불러오기: 종료·재실행 유지, 파일 없음·손상 및 저장 오류 확인.
7. 최종 점검: 종료 처리, 브랜치·병합, 노트북·공용 컴퓨터 동기화, 증빙 정리.

번호 입력 검증은 입력 기능과 함께 추가한다. 다중 파일 분리는 기능의 역할과 import를 설명할 수 있게 된 뒤 필요에 따라 진행한다.

## README 정리 방향

현재 README에는 작업 기록, 문법 설명, 계획, 제출 안내가 함께 있고 약 2,700줄이라 현재 해야 할 일을 찾기 어렵다. 현재 상태를 짧게 보여주는 README와 상세 기록을 연결하는 구성으로 점진적으로 정리한다.

| 문서 | 담을 내용 |
|---|---|
| README.md | 개요·주제 이유·실행 방법·현재 기능 상태·파일 구조·저장 방식·검증 요약·기록 링크 |
| docs/game-development-log.md (예정) | 현재 새 게임의 상세 작성 과정과 코드 변경·실제 출력·해설 |
| docs/python-notes.md (예정) | 변수·클래스·리스트·반복문 등 문법 설명 |
| docs/git-guide.md (예정) | Git 명령 해설과 두 컴퓨터의 작업 순서 |
| docs/test-results.md (예정) | 테스트 방법·기대 결과·실제 결과·증빙 |

예정 문서는 아직 생성하지 않았다. 기존 기록을 옮길 때는 코드 블록·이미지·상대 링크를 함께 확인한다. README에는 현재 확인된 상태를 적고, 각 기록에는 당시 확인 범위를 남긴다. 이전 게임의 완료 기록을 새 게임 결과로 넣지 않는다.

기록 형식은 실행 위치와 주석이 있는 명령 블록 → 실제 출력 블록 → 해설 순서를 유지한다. 소스 수정 단계는 수정 전후 코드와 변경 위치를 먼저 보여 준다. 실행하지 않은 예상 출력은 실제 출력과 구분한다.
